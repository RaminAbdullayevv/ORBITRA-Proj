# ORBITRA layihə müqaviləsi — mərhələ 8

## Struktur və məsuliyyət

- `frontend/`: React səhifələri (`src/pages`), API tipləri (`src/lib/api.ts`) və canlı səhifələrin ortaq telemetriya/hadisə/WS məntiqi (`src/lib/useLiveTelemetry.ts`). Sensor və simulyasiya vaxtı burada hesablanmır.
- `backend/`: FastAPI (`app/main.py`), `/api/v1` route-ları (`app/api`), tək lokal virtual cihaz modeli (`app/simulator.py`), commit və yayım qatı (`app/telemetry.py`), yalnız qəbul edilmiş telemetriyanı qiymətləndirən lokal model (`app/ai_analysis.py`), SQLite modelləri (`app/models.py`) və Alembic (`alembic/`).
- `backend/tests/`: vaxtı idarə olunan simulator və telemetriya testləri. `docs/`: inkişaf və təhvil qaydaları.

## Sabit qaydalar

- Bütün tətbiq endpoint-ləri `/api/v1` prefiksi altındadır. Köhnə `GET /health` və `GET /app-info` saxlanır.
- Virtual cihaz: `GET /virtual-device` və `POST /virtual-device/{start,pause,resume,reset,end,reduce-processing-load}`. Start istəyə bağlı `scenario` sahəsində `NORMAL_MISSION`, `TEMPERATURE_ANOMALY`, `INVALID_TELEMETRY`, `SINGLE_SENSOR_FAULT`, `INVALID_SIGNATURE` və ya `REPLAYED_TELEMETRY` alır; body yoxdursa normal seçilir. Cavabın vahid strukturu `schema_version`, `run_id`, `scenario`, `status`, `simulation_elapsed_seconds`, `system_mode`, `subsystem_statuses`, `sensors`, `updated_at` sahələrindən ibarətdir. Uyğun olmayan vəziyyət keçidi `409 invalid_transition` qaytarır.
- Backend konfiqurasiyası `backend/.env` və ya mühit dəyişənlərindən oxunur. `DATABASE_URL` lokal SQLite bazasını, `FRONTEND_ORIGIN` tək icazəli frontend origin-ini müəyyən edir. Frontend `VITE_API_BASE_URL` istifadə edir. `.env.example` faylları nümunədir; `.env` və SQLite Git-ə daxil edilmir.
- Route-lar: `/mission-control`, `/virtual-device`, `/ai-alerts`, `/security`, `/digital-twin`, `/mission-report`, `/telemetry-trust`. `/` Mission Control-a yönləndirilir. Bütün canlı səhifələr eyni run və saxlanmış telemetriya/hadisələrdən istifadə edir.
- Ümumi UI komponentləri real backend vəziyyətini göstərməli, klaviatura fokusunu görünən saxlamalı və olmayan funksiyaya işlək düymə qoymamalıdır. Xəta zamanı köhnə sensor rəqəmləri canlı kimi saxlanmamalıdır.
- Virtual Device məlumatı frontend-də ayrıca saxta generatorla yaradılmır. Digital Twin gələcəkdə yalnız qəbul edilmiş telemetriyanı göstərəcək; hazırkı simulatorun daxili vəziyyətini avtomatik “qəbul edilmiş paket” saymaq olmaz.
- Backend-də bir aktiv lokal cihaz var. Vəziyyət yaddaşdadır və proses yenidən başlayanda IDLE-a qayıdır. Açıq run `INTERRUPTED` kimi bağlanır; saxlanmış tarixçə qalır. `0004_scenarios` run ssenarisini, qayda xəbərdarlıqlarını və rədd edilmiş nümunələri; `0005_ai_analysis` model metadata-sı və AI hadisələrini; `0006_security` hesab, sessiya, audit və insidentləri əlavə edir. Sonrakı schema dəyişikliyi ayrıca Alembic migrasiyası almalıdır.
- Sonrakı mərhələlər mövcud route-ları, health yoxlamasını və işləyən simulator əməliyyatlarını qoruyaraq əlavə edilir.

## Canlı telemetriya müqaviləsi

- `GET /api/v1/telemetry/state` aktiv cihazı, ssenarili run-u, son saxlanmış nümunəni, `active_alerts`, `rule_alerts`, `rejections`, `ai_status` və `ai_events` qaytarır. `run_id` parametri tarixi run-u seçir; onun `device` sahəsi aktiv deyilsə `null` olur. `GET /api/v1/telemetry/runs/{run_id}/ai-events` tarixi AI hadisələrini oxuyur.
- `GET /api/v1/telemetry/runs/{run_id}/samples` artan sıra ilə tarixçə qaytarır. `after_sequence` və `limit` (`1..600`) boşluq tamamlama üçündür; parametrsiz son `limit` nümunə qaytarılır.
- `GET /api/v1/telemetry/runs/{run_id}/events` artan `event_number` ilə operator tarixçəsi qaytarır. `after_id` və `limit` (`1..600`) yenidən qoşulma və tam tarixçə üçündür.
- `WS /api/v1/telemetry/ws` əvvəl `simulation_status`, sonra `telemetry_sample`, `operator_event`, `rule_alert`, `telemetry_rejected`, `ai_assessment`, `ai_event`, status dəyişiklikləri və təxminən 3 saniyəlik `heartbeat` verir. Nümunədə `type`, `run_id`, `sequence_number`, `simulation_elapsed_seconds`, `sample_time`, `status` və bütün 11 sensor olur. Statusda `device`, `run`, `latest_sample`, `rule_alerts`, `rejections`, `ai_status`, `ai_events`; heartbeat-də `sent_at`, `run_id`, `status` olur. AI hadisəsi `event_id` və `run_id` ilə təkrarsız birləşdirilir.
- Nümunə yalnız SQLite commit-dən sonra yayımlanır. `(run_id, sequence_number)` unikal olduğu üçün təkrar yazılış ikinci qeyd yaratmır. Frontend də eyni açar üzrə təkrarları ayırır və yalnız cari run-un son 300 saniyəsini göstərir.
- Start IDLE/ENDED-dən yeni run açır və ssenarini run ilə saxlayır; Pause nümunə və vaxtı dondurur; Resume yalnız PAUSED run-u davam etdirir; End RUNNING/PAUSED run-u ENDED terminal vəziyyətində saxlayır; Reset IDLE edir və aktiv run-u `RESET` kimi bağlayır. Aktiv run-da ssenari dəyişmir. ENDED run-dan sonra Reset onun tarixi statusunu dəyişmir. End və Reset tarixi silmir. `reduce_processing_load` yalnız RUNNING zamanı hər run üçün bir dəfə CPU hədəfini 20%-ə endirir; cərəyan və istilik sonrakı sensor addımlarında tədricən dəyişir.
- Hər qəbul edilmiş və ya rədd edilmiş operator sorğusu SQLite-da `event_id`, `event_number`, `run_id`, `action`, `received_at`, `simulation_elapsed_seconds`, `before_status`, `after_status`, `outcome`, `reason`, `source`, `user_id` ilə saxlanır. Yayımdan əvvəl commit edilir. Frontend tarixçə və WS hadisələrini `event_id` ilə ayırır. Köhnə `local_demo_operator` etiketli tarixçənin `user_id` dəyəri boşdur; yeni əməliyyatlar autentifikasiya olunmuş Operator-a bağlanır.
- Qoşulur, canlı, istifadəçi tərəfindən dayandırılıb, kəsilib, köhnəlib və məlumat yoxdur halları ayrı göstərilir. RUNNING zamanı yeni nümunə gecikirsə son dəyər canlı sayılmır; PAUSED zamanı nümunənin gəlməməsi gözləniləndir. Yenidən qoşulanda son sıra nömrəsindən sonrakı nümunələr HTTP ilə tamamlanır.

## Mission Control qiymətləndirmə qaydaları

System Health yalnız etibarlı son nümunəni aşağıdakı Mərhələ 8 qayda cədvəlinə əsasən qiymətləndirir. Bunlar təsdiqlənmiş mühəndislik hədləri deyil. PAUSED zamanı dəyərlər sabitdir; bağlantı kəsiləndə, məlumat köhnələndə və ya run ENDED olduqda “Normal” göstərilmir.

Active Alerts yalnız backend vəziyyətinin `active_alerts` sahəsində olan qayda xəbərdarlıqlarını göstərir. Temperatur 1 ≥24.5 °C və paket itkisi ≥0.5% ayrı qaydalardır; bərpa hədləri müvafiq olaraq ≤23.3 °C və ≤0.3%-dir. Açılma və bağlanma vaxtı SQLite-da qalır. Bu AI təhlili deyil. Bağlantı yoxdursa “xəbərdarlıq yoxdur” iddia edilmir.

## Sonrakı mərhələ sərhədləri

Üç ssenari eyni simulator, sabit başlanğıc sensorları və hər ssenari üçün sabit random seed işlədir. `NORMAL_MISSION` yalnız kiçik normal dəyişikliklər verir. `TEMPERATURE_ANOMALY` T+8-də CPU hədəfini artırır və cərəyan/istiliyi tədricən dəyişir. `INVALID_TELEMETRY` T+10-da `schema_version=9.9-test` nümunəsini eyni qəbul yoluna verir. Qəbul yolu yalnız `1.0` dəstəkləyir: #10 `telemetry_samples` və `telemetry_sample` WS axınına yazılmır, `rejected_telemetry`-da səbəb/run/sıra/vaxt saxlanır; #11 və sonrakılar qəbul olunur. Format rəddi hücum sübutu deyil.

Demo ardıcıllığı: Normal Start → göstəricilər → End → Temperature Start → yük/cərəyan/istilik və qayda xəbərdarlığı → Reduce → tədrici bərpa və Timeline → End → Invalid Start → Security Operations rəddi və qrafikdə #10 boşluğu. Reset ilkin sensor vəziyyətini qaytarır. Yeni run köhnə run-un xəbərdarlıq/rədd qeydlərini daşımır; tarixçələr bazada qalır. AI modulu yalnız `telemetry_samples` cədvəlindəki qəbul edilmiş `run_id`/`sequence_number` sırasını oxuyur. `rejected_telemetry` yalnız rədd izidir, AI ölçmə girişinə daxil deyil. Mission Report Mərhələ 8-də qurulub.

## Mərhələ 6 AI müqaviləsi

- `scripts/train_ai.py` eyni simulatorla yalnız normal sessiyalardan 20 saniyəlik xüsusiyyət pəncərələri yaradır. Təlim, kalibrasiya və yekun testlər **ayrı sessiya seed-ləri** ilə aparılır. Bəzi normal sessiyalarda T+45-də mövcud virtual yük azaltma əmri var; modelə əmrin özü verilməyib. `model_artifacts/metadata.json` seed-lər, versiya, baza statistikası, kalibrasiya həddi, scikit-learn versiyası və artifact SHA-256 saxlayır. `training_report.json` ayrıca sintetik yekun nəticədir.
- AI girişinə yalnız `TelemetryStore.process_sample` tərəfindən **commit edilmiş** `telemetry_samples` sətirləri daxil olur. `run_id` və `sequence_number` pəncərə bütövlüyünü qoruyur; xüsusiyyət vektorunda ssenari adı, seed, fault vaxtı/etiketi, daxili simulator bayrağı və operator əmri yoxdur. Rədd edilmiş #10 və fasilə zamanı yeni qiymətləndirmə yoxdur. 20 ardıcıl qəbul edilmiş nümunə olmadıqda bal `null` qalır.
- Isolation Forest-in `-score_samples` dəyəri yüksək olduqca normal pəncərələrdən fərq artır; bu ehtimal/faiz deyil. Ayrı kalibrasiya normal sessiyalarında üç ardıcıl anomal pəncərə ilə sıfır təsdiqlənmiş hadisə verən ən aşağı hədd seçilir. Üç ardıcıl pəncərə hadisə açır, 10 ardıcıl normal pəncərə onu bağlayır. Davam edən hadisə tək `event_id` ilə yenilənir. `ai_events` run, başlanma/yenilənmə/bitmə vaxtları, sıra və pəncərə, sensorlar, bal, normal baza fərqləri, versiya və müşahidəyə əsaslanan Azərbaycan dilində izah saxlayır.
- AI yalnız müşahidə edir. Operator əmri icra etmir. Model artifact-i yalnız layihənin sabit `backend/model_artifacts/` qovluğundan SHA-256 və scikit-learn versiyası yoxlanaraq oxunur. Model yoxdursa və ya xətalıdırsa telemetriya qəbul/yayım axını davam edir; UI “AI hazır deyil” göstərir. Backend restartında əvvəlki AI hadisələri SQLite-dan oxunur, aktiv run isə əvvəlki mərhələlərdə olduğu kimi davam etmir.
- Mənbələr ayrı göstərilir: kritik temperatur və yüksək paket itkisi **Qayda**; normaldan fərqli davranış **AI analizi**; RUNNING zamanı təzə qəbul edilmiş məlumatın olmaması **Məlumat keyfiyyəti**; rədd edilmiş format **Təhlükəsizlik yoxlaması**. PAUSED gözlənən dayanmadır. Eyni vaxtda qayda və AI ola bilər; bunlar eyni hadisə və ya sübut olunmuş nasazlıq səbəbi kimi birləşdirilmir.
- Yekun ayrıca sintetik yoxlama `training_report.json` içindədir; rəqəmlər real raket üçün dəqiqlik iddiası deyil. Model yalnız bu sadə lokal tədris paylanmasına öyrədilib. Missiya Hesabatı Mərhələ 8-də qurulub.

## Mərhələ 7 təhlükəsizlik müqaviləsi

- İlk quraşdırmada `python -m alembic upgrade head`, sonra `python -m scripts.setup_security` işlədilir. İkinci addım `.env`-də 32 baytlıq HMAC açarı yaradır və lokal `admin`/`ADMIN` hesabını yalnız yoxdursa Argon2 hash ilə yaradır. Hazır `admin / admin` giriş məlumatı yalnız lokal virtual sınaq təqdimatı üçündür; giriş serverdə loopback ilə məhdudlaşdırılır. Tarixi `operator`, `analyst`, `observer` rolları və hesab qeydləri saxlanır, lakin yeni demo rol dəyişmədən admin ilə idarə olunur.

- Bütün cihaz əmrləri və ssenari seçimi Operator və ya Admin-ə açıqdır. Bütün rollar mövcud telemetriya, AI, audit və insidentləri oxuya bilər. Analyst və ya Admin insidentə qeyd yaza və səbəb göstərərək bağlaya bilər. Rol qərarı serverdə verilir; UI deaktiv düymələri həmin qərarı izah edir. Telemetriya redaktə endpoint-i yoxdur.
- `/api/v1/auth/login`, `/me`, `/logout` server sessiyasını idarə edir. Sessiya tokeninin yalnız SHA-256 izi bazada saxlanır; brauzer tokeni `HttpOnly` cookie-də saxlayır. Sessiya 8 saatdan sonra və logout zamanı etibarsızdır. Eyni istifadəçi adı üçün 10 dəqiqədə 5 uğursuz cəhd limitdir. Mutasiya sorğularında frontend origin-i və sessiyadan törədilmiş CSRF başlığı, WS-də cookie və origin yoxlanır. Lokal HTTP üçün `COOKIE_SECURE=false`, HTTPS üçün `true` təyin edilir.
- Simulator nümunəni HMAC-SHA256 ilə imzalayır; canonical məzmun schema, run, source, sıra, vaxt, status və bütün sensorları əhatə edir. Qəbul yolu `SCHEMA_REJECTED`, `INTEGRITY_REJECTED`, `SOURCE_REJECTED`, `REPLAY_REJECTED`, `STALE_REJECTED` kodlarını ayırır. Eyni run/source/sıra ikinci dəfə normal telemetriyaya yazılmır. Rədd və icazə qərarları `audit_events`, telemetriya rədləri isə `security_incidents`-də saxlanır. Köhnə rədd qeydləri tarixi insidentə çevrilir; köhnə qəbul edilmiş telemetriyanın imzası geriyə dönük yoxlanmır.
- Security Operations son 200 audit və insidenti göstərir; bazadakı köhnə qeydlər silinmir. Analyst/Admin qeydi müəllif, vaxt və mətnlə; bağlama qərarı müəllif, vaxt və səbəblə saxlanır. Təkrar eyni rədd səbəbi və sıra üçün `rejected_telemetry` qeydinin təkrar yazılması əngəllənir; hər cəhd ayrıca trust assessment, audit və insidentdə qalır. Simulator və yoxlayıcı eyni lokal backend prosesindədir; proses tam ələ keçirilərsə imza müstəqil müdafiə deyil. Bu lokal demo tamper/replay nümunəsini göstərir, həqiqi uçuş təhlükəsizliyi zəmanəti vermir.

## Sentinel müqaviləsi

- `0008_sentinel` `telemetry_trust_assessments` cədvəlini yaradır, mövcud `rejected_telemetry` cədvəlini nullable sübut sahələri ilə genişləndirir. Köhnə telemetriya və istifadəçi qeydləri silinmir. Ayrı Sentinel event cədvəli əvəzinə mövcud `security_incidents` və `audit_events` istifadə edilir.
- Format → mənbə → HMAC imzası → monoton sıra/replay → UTC freshness qapıları qəbuldan əvvəl işləyir. Qapıdan keçməyən paket qəbul edilmiş telemetriya, qrafik, Rule Engine, Digital Twin və AI-yə getmir. Hər paketə ayrıca trust qərarı yazılır; qayda versiyası və ölçmə sübutları saxlanır.
- Qəbul edilmiş nümunələrdə sensor və tədris Digital Twin uyğunluğu sistem anomaliyası ilə tək sensor xətasını ayırır. Sentinel ehtimal edilən texniki səbəb bildirir; AI yalnız qəbul edilmiş davranış fərqini müşahidə edir; Rule Engine sabit hədləri yoxlayır. Bu qərarlar real uçuş hədləri və ya hücum təsdiqi deyil.

## Mərhələ 8: qəbul edilmiş məlumat, Digital Twin və hesabat

- Virtual Device sintetik nümunə yaradır; Digital Twin yalnız backend-in imza/format/mənbə yoxlamasından sonra SQLite-da qəbul etdiyi son nümunəni oxuyur. Rədd paketin sensor dəyəri Mission Control, Digital Twin, qayda hesabı və AI girişinə keçmir. İkinci idarəetmə və gizli simulator vəziyyəti oxunuşu yoxdur.
- Mission Control və Digital Twin canlı vəziyyət üçün bir `frontend/src/lib/subsystems.ts` modulundan istifadə edir. Yekun Mission Report yalnız qəbul edilmiş son nümunəyə tətbiq edilən eyni versiyalı Python qaydasını (`backend/app/subsystems.py`) istifadə edir. Qayda versiyası `teaching-health-v1` kimi saxlanır.
- Hədlər yalnız tədris üçündür. Enerji WARNING: batareya <20% və ya gərginlik <25 V; CRITICAL: <10% və ya <23 V. İstilik WARNING: uyğun temperatur ≥24.5 °C və ya aktiv temperatur qaydası; CRITICAL: uyğun temperatur ≥30 °C. Sentinel tək sensor nasazlığı qərarı veribsə, yalnız digər iki temperatur kanalı istilik blokunu qiymətləndirir. Rabitə WARNING: siqnal <80%, gecikmə >60 ms, itki ≥0.5% və ya aktiv itki qaydası; CRITICAL: siqnal <60%, gecikmə >100 ms və ya itki ≥1%. Kompüter WARNING: CPU >40% və ya yaddaş >80%; CRITICAL: CPU >70% və ya yaddaş >90%.
- RUNNING zamanı yeni etibarlı nümunə təxminən 4.5 saniyə gəlmirsə və ya WebSocket kəsilibsə dörd cari status UNKNOWN olur; son qəbul edilmiş vaxt və dəyər tarixi kimi qalır. PAUSED üçün dayandırılma gözlənəndir və nasaz rabitə hadisəsi sayılmır. ENDED-də canlı status UNKNOWN olur, hesabat isə yekun etibarlı nümunənin vəziyyətini ayrıca göstərir.
- Mission Report `run_id` üzrə `telemetry_samples`, rədd/insident, qayda, AI, audit və operator cədvəllərini oxuyur. Üç ssenari bir hesabata qarışmır. Aktiv run yalnız “İlkin görünüş”dür. ENDED run üçün `report_generations` cədvəlində yaradılma vaxtı, run ID, qayda və model versiyası saxlanır. `run_analysis` cədvəli qəbul edilmiş ardıcıl pəncərə üzrə AI qiymətləndirməsinin izini saxlayır; iz yoxdursa UI AI analizinin əlçatan olmadığını deyir.
- `0007_reports` migrasiyası iki metadata cədvəlini yaradır və köhnə AI hadisələrindən mümkün qiymətləndirmə izini bərpa edir. Köhnə qəbul edilmiş telemetriya/insidentlər silinmir. Hesabatın oxunması hər üç autentifikasiya olunmuş rola açıqdır. Metadata yaratma eyni origin və CSRF tələb edir; cihaz əmrləri yenə yalnız Operator-a, insident qeydi/bağlama yalnız Analyst-ə məxsusdur.
- PDF üçün brauzerin A4 print funksiyası işlədilir. Print CSS tünd UI-ni açıq sənədə çevirir, idarəetməni gizlədir, uzun siyahıların səhifələnməsini və hər səhifədə run ID başlığını nəzərdə tutur. Xarici PDF xidməti yoxdur.

Bu ekranların nəticələri real aparat sağlamlığı, nasazlıq ehtimalı və ya uçuş təhlükəsizliyi zəmanəti kimi istifadə edilə bilməz.
